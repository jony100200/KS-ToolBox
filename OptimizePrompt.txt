# KS Toolbox Deterministic-First Architecture and Optimization Audit

You are working inside the **KS Toolbox** repository.

KS Toolbox is a local-first desktop application containing multiple practical tools for everyday file, document, image, media, development, and batch-processing activities.

Your task is to inspect the entire application and determine whether it follows a **deterministic-first, cartridge-disciplined architecture** without reducing, removing, or weakening any user-facing functionality.

Do not assume that AI is undesirable. AI models are allowed and may be essential for some features.

The governing rule is:

> Use deterministic algorithms, existing structured data, retrieval, rules, reusable procedures, and specialist tools whenever they can produce an equal or better result. Use an AI model only when it provides meaningful functionality or quality that simpler methods cannot provide.

The objective is not merely to reduce application size. Optimize the complete system:

* package size;
* installed size;
* startup time;
* idle RAM;
* active RAM;
* VRAM;
* CPU use;
* disk reads and writes;
* temporary storage;
* model-loading time;
* processing latency;
* dependency count;
* reliability;
* maintainability;
* portability;
* user experience.

Do not remove functionality simply to achieve a smaller measurement.

## Primary objectives

Determine:

1. Which operations are already deterministic.
2. Which operations unnecessarily invoke AI.
3. Which operations genuinely benefit from AI.
4. Which AI calls can be avoided through confidence checks, caching, retrieval, templates, rules, classifiers, or reusable procedures.
5. Which dependencies are unused, duplicated, oversized, or unnecessarily loaded.
6. Which workflows repeat work that could be cached or resumed.
7. Which batch operations can be streamed, fused, parallelized, or processed incrementally.
8. Which components are initialized even when the current tool does not need them.
9. Whether KS Toolbox can remain portable and plug-and-play.
10. How much optimization is possible without losing any existing capability.

## Non-negotiable constraints

Do not:

* remove working features;
* weaken output quality without explicit evidence and approval;
* replace a reliable component with a fragile custom implementation merely to reduce size;
* change public interfaces unnecessarily;
* silently change file formats or output structures;
* introduce mandatory cloud services;
* add Docker as a normal runtime requirement;
* require users to manually install dependency chains;
* load an AI model for deterministic operations;
* load GPU libraries for CPU-only tasks;
* initialize every module during application startup;
* introduce unrestricted shell execution;
* permit model-generated actions to bypass validation;
* optimize based only on assumptions.

Preserve backward compatibility where practical.

When a breaking change appears necessary, document:

* why it is necessary;
* what functionality it affects;
* migration steps;
* rollback options;
* measurable benefits.

## Phase 2: Feature-to-mechanism map

Create a map of every user-facing feature and the mechanisms it uses.

Classify each operation into one of these levels:

### Level 0 — Exact deterministic operation

Examples:

* file copying;
* renaming;
* hashing;
* archive extraction;
* metadata reading;
* format validation;
* dimensions and resolution checks;
* regular-expression matching;
* sorting;
* grouping;
* checksums;
* duplicate detection by exact hash;
* mathematical calculations;
* deterministic templates.

These operations should never require a generative model.

### Level 1 — Deterministic heuristic or algorithm

Examples:

* perceptual hashing;
* fuzzy filename matching;
* image-quality metrics;
* scene-change detection;
* anomaly thresholds;
* rule-based categorization;
* clustering;
* ranking;
* constraint solving;
* static analysis.

Use AI only when these methods cannot reach acceptable accuracy.

### Level 2 — Small specialist model

Examples:

* compact embeddings;
* image similarity;
* language detection;
* classification;
* OCR;
* speech recognition;
* object detection;
* face or identity similarity;
* anomaly detection.

Prefer a specialist model over a general language or vision-language model when it provides sufficient quality.

### Level 3 — Small generative model

Use for:

* interpreting unclear natural-language requests;
* extracting parameters from flexible instructions;
* structured workflow planning;
* captioning ambiguous media;
* summarizing unstructured content;
* explaining unusual errors.

Require structured outputs and validation.

### Level 4 — Large model escalation

Use only for:

* genuinely novel reasoning;
* complicated semantic interpretation;
* difficult multimodal understanding;
* advanced code generation or repair;
* cases where smaller methods demonstrably fail.

For every AI-assisted feature, explain why Levels 0–2 are insufficient.

## Phase 3: AI-call audit

Find every location where KS Toolbox calls:

* local LLMs;
* local VLMs;
* remote AI APIs;
* LM Studio;
* llama.cpp;
* ComfyUI;
* OCR engines;
* transcription models;
* embedding models;
* classifiers;
* image-generation models;
* video-generation models.

For each call, record:

* triggering feature;
* input size;
* output type;
* model name;
* RAM and VRAM usage;
* cold-start cost;
* average execution time;
* whether the model remains loaded;
* whether results are cached;
* whether identical work is repeated;
* whether the output is validated;
* deterministic alternatives;
* smaller-model alternatives;
* conditions under which the call can be skipped.

Identify AI calls that can be avoided by:

* checking whether the answer already exists;
* exact cache lookup;
* content hashing;
* retrieving a previous successful procedure;
* detecting unchanged inputs;
* using a template;
* using a parser;
* using a classifier;
* using metadata;
* using structured extraction;
* using confidence thresholds;
* asking the user one precise question;
* reusing previous outputs.

The correct routing cascade should normally be:

```text
Exact command or rule
→ existing compiled procedure
→ cached previous result
→ retrieved similar procedure
→ deterministic heuristic or solver
→ specialist model
→ small generative model
→ optional larger model
```

Do not invoke every stage. Stop as soon as a trustworthy result is available.

## Phase 4: Batch-processing audit

KS Toolbox performs daily batch operations, so inspect all batch workflows for:

* repeated file decoding;
* repeated hashing;
* repeated model inference;
* unnecessary format conversions;
* loading complete files when streaming is possible;
* excessive temporary files;
* unbounded queues;
* copying large data between stages;
* serial execution of independent operations;
* excessive parallelism causing disk or VRAM contention;
* restarting completed work after failure;
* missing progress checkpoints;
* missing cancellation;
* missing retry boundaries;
* GPU initialization for non-GPU work;
* models repeatedly loading and unloading within one batch.

For each batch tool, design an optimized execution graph.

Example:

```text
Discover files
→ calculate content identity
→ skip unchanged files
→ validate formats
→ group compatible operations
→ execute deterministic stages
→ route only uncertain items to AI
→ verify outputs
→ retry failed items only
→ commit outputs atomically
→ update manifest and cache
```

Measure how many inputs require AI rather than assuming the entire batch needs AI.

## Phase 5: Content-addressed caching

Assess whether KS Toolbox can cache results using a key derived from:

```text
tool version
+ operation settings
+ input content hashes
+ relevant model version
+ workflow version
+ environment factors affecting the result
```

Identify reusable intermediate outputs such as:

* file hashes;
* decoded metadata;
* thumbnails;
* perceptual hashes;
* OCR text;
* transcripts;
* embeddings;
* image masks;
* quality scores;
* extracted document text;
* model captions;
* converted media;
* workflow outputs.

Ensure cache entries include provenance and can be invalidated correctly.

Do not cache nondeterministic outputs as though they were deterministic. For AI-generated results, include the model, sampler, seed, prompt, workflow, and configuration where applicable.

## Phase 6: Incremental execution

Determine whether jobs can recompute only affected stages.

Example:

```text
1,000 files processed
1 file changes
```

The system should not repeat work for the other 999 files unless the changed file affects a global result.

Design dependency tracking between:

* source files;
* intermediate artifacts;
* workflow stages;
* final outputs;
* reports;
* indexes;
* model-generated data.

Recommend where incremental recomputation would provide the largest benefit.

## Phase 7: Procedure reuse

Inspect whether repeated workflows are currently reconstructed manually or regenerated by AI.

Design a safe procedure-reuse system where successful work can become a reusable parameterized procedure.

Example requests:

```text
Resize all PNG files to 1024×1024.
Resize all JPEG files to 512×512.
Resize these character images to 2048×2048.
```

These should become one reusable procedure:

```text
resize_batch(input, format_filter, width, height, output)
```

Procedure promotion must require:

* successful execution;
* validated outputs;
* parameter identification;
* removal of file-specific constants;
* regression tests;
* versioning;
* rollback;
* human approval for risky operations.

Do not treat exact prompt caching as true procedure learning.

The scheduler should understand:

* disk-bound jobs;
* network-bound jobs;
* interactive jobs;
* background batch jobs;
* exclusive resources;
* available VRAM;
* model residency;

## Implementation policy

Do not begin broad refactoring immediately.

Follow this order:

1. Inventory.
2. Baseline measurements.
3. Architecture analysis.
4. Deterministic-versus-AI classification.
5. Opportunity ranking.
6. Low-risk prototype.
7. Before-and-after benchmark.
8. Regression tests.
9. Implementation only when benefits are demonstrated.
10. Update documentation and rollback instructions.

You may implement safe, isolated optimizations after the audit when all of the following are true:

* behavior is well understood;
* tests exist;
* functionality is preserved;
* rollback is straightforward;
* measurable benefit is likely;
* the change does not force unrelated architectural decisions.

Do not implement high-risk changes without first documenting them and obtaining approval.

3. How many model calls can be eliminated without reducing quality?
4. Which successful AI operations can become reusable procedures?
5. Which dependencies contribute the most package size?
6. Which dependencies are duplicated or loaded unnecessarily?
7. Which tools redo work that can be cached?
8. Which workflows can become incremental?
9. Which batch operations can be streamed or fused?
10. Which models can remain unloaded until required?
11. What causes the largest startup and idle-memory costs?
12. Can the application remain fully portable?
13. What can be reduced safely?
14. What should not be reduced because it would damage quality or reliability?
15. What is the smallest practical package that preserves the complete KS Toolbox experience?
16. What five changes provide the largest benefit for the least risk?

## Final principle

Optimize KS Toolbox as though every megabyte, model call, allocation, process, dependency, and line of code must justify its existence.

However:

> Never confuse minimalism with removing capability.

The goal is to make KS Toolbox smaller, faster, more reliable, more portable, and less dependent on AI while preserving—or improving—everything useful that it already does.
